# AI Debate Room

여러 AI가 하나의 주제로 다라운드 토론하고, 별도 Judge AI가 전체를 평가해 결론을 내리는
멀티 에이전트 시스템.

> **현재 상태: v1 완료.** 네 슬라이스 모두 끝났고 Gemini 라이브에서 완주를
> 확인했습니다. 아래 [실측 기준값](#실측-기준값-v1-2026-09)이 다음 세팅의 기준입니다. 라이브 스모크는 슬라이스 1 시점에 통과했습니다.
> 골격과 검증만 있습니다. Judge · 다라운드 · 쟁점 추출 · 저장 · API · UI 는 아직 없습니다.
> 실제 모델 호출 경로(`OpenAICompatProvider`)는 구현·테스트돼 있지만 **진짜 프로바이더로는
> 아직 한 번도 안 돌려봤습니다.** 아래 [라이브 스모크 3단계](#라이브-스모크-3단계)를
> 먼저 통과시킨 뒤 슬라이스 2 로 갑니다.

## 실측 기준값 (v1, 2026-09)

새 환경에서 세팅할 때 "제대로 돌고 있는지" 판단하는 기준입니다. 모두 Gemini
(`gemini-3.5-flash-lite` 참가자 / `gemini-3-flash-preview` 심판) 라이브 측정치입니다.

### 규모와 비용 — 참가자 2명 · 2라운드 · judge 포함

| 항목 | 값 |
|---|---|
| 요청 수 | **6회** (발언 4 + 쟁점 추출 1 + 판정 1) |
| 총 토큰 | **약 7,000** (실측 6,777 / 7,067) |
| 판정 복구가 붙으면 | **약 9,300** (실측 9,239 / 9,312, 판정 2회) |
| 심판이 Groq (`openai/gpt-oss-120b`) | **8,747** (복구 없음 — 견적 상한 초과, 원인 미확인) |
| 견적 범위 | 5,7xx ~ 7,1xx + 복구 시 +2,520 |

복구 몫을 본 범위에 섞지 않고 따로 내는 이유가 여기 있습니다. 복구 있는 실행
두 건(9,239 / 9,312)이 모두 `범위 상한 + 2,520` 안에 들어오고, 복구 없는 실행
두 건(6,777 / 7,067)은 범위 안에 들어옵니다. 하나로 합쳤다면 5,7xx~9,6xx 라는
1.7배짜리 범위가 되어 "보통 얼마"인지를 잃습니다.

요청 수가 6이 아니면 뭔가 어긋난 겁니다. 7이면 판정이 한 번에 파싱되지 않아
복구가 붙은 것이고(`verdicts.parse_attempts = 2`), 5면 판정이 아예 안 돈 것입니다.

한국어 발언 1건은 **172~319 토큰 / 250~450자**, 토큰 계수 **0.71 토큰/자**.
다른 벤더를 붙이면 토크나이저가 달라지므로 다시 재야 합니다.

#### 견적이 실제로 맞는지 — 측정 4건

| 실행 | 견적 | 실제 | 판정 |
|---|---|---|---|
| 입장 지정 | 5,810 ~ 7,140 | 6,777 | 범위 안 |
| 입장 지정 | 5,774 ~ 7,176 | 7,067 | 범위 안 |
| 입장 미지정 + 복구 | 5,702 ~ 7,104 **+ 2,520** | 9,239 | 범위 안 |
| 입장 미지정 + 복구 | 5,714 ~ 7,116 **+ 2,520** | 9,312 | 범위 안 |

견적이 크게 빗나가면 대개 **판정 복구를 세지 않은 것**입니다. `llm_calls` 에서
`purpose='judge'` 행이 2개면 복구가 붙은 것이고, 그때는 `+2,520` 을 더한 값과
비교해야 합니다.

### 지연

| 대상 | 실측 |
|---|---|
| 참가자 (`gemini-3.5-flash-lite`) | 2초 내외 |
| 참가자 (느린 경우) | 최대 54초 — 30배 편차를 봤습니다 |
| **심판 (`gemini-3-flash-preview`)** | **3~4분** |
| 심판 (`groq/openai/gpt-oss-120b`) | 즉시 — 체감 지연 없음 |

심판이 참가자보다 두 자릿수 느립니다. 사고 과정을 출력 예산에서 함께 쓰는
모델로 보입니다. `DEBATE_JUDGE_TIMEOUT_S` 기본 300초는 이 실측 때문입니다 —
180초면 정상 판정을 중간에 끊습니다.

### 토론 품질 — 입장 지정 여부가 가릅니다

같은 주제·같은 모델로 입장만 다르게 해서 돌린 두 실행입니다.

| | **입장 지정** | **입장 미지정** |
|---|---|---|
| R1 | 각자 자기 입장에서 입론 | 둘 다 찬성으로 **수렴** (근거까지 거의 동일) |
| R2 | 서로 다른 근거로 같은 쟁점에서 충돌 | 둘 다 반대로 **번복** — 자기 R1 주장을 스스로 반박 |
| **일관성** | **10 / 10** | **2 / 2** |
| 논리 | — | 4 / 5 로 하락 |
| 반박 | — | 5 / 7 로 하락 |
| 루브릭 합계 | **44 / 40** | **25 / 30** |
| Judge 결론 | `dissent` 가 실제 일어난 일을 요약 | "양측 모두 입장을 번복했으나" 를 명시 |

**`일관성` 이 이 시스템의 상태 표시등입니다.** 10 근처면 토론이 성립한 것이고,
한 자릿수 초반이면 참가자들이 라운드마다 입장을 갈아타고 있습니다. 입장을
뒤집으면 논리·반박 점수까지 함께 떨어지므로 합계 격차가 크게 벌어집니다
(44/40 대 25/30).

축이 깨지면 이 차이가 먼저 사라집니다 — 입장 없이 돌렸는데 일관성이 높게
나오면 채점이 아니라 코드를 의심하십시오.

### 정상 실행의 모양

**입장을 지정하고 돌렸을 때:**

```
요청 6회 · 토큰 ~7,000 · 판정 1회(parse_attempts=1) · dropout 0
쟁점 3~5개 추출 · 발언마다 finish_reason='stop'
일관성 8~10 · 루브릭 합계 40 안팎
```

**입장 없이 돌렸을 때 (이것도 정상 동작입니다):**

```
일관성 2~4 · 루브릭 합계 25~30
Judge 결론에 입장 번복이 언급됨
UI 에 "입장 미지정 N명" 안내 표시
```

두 모양이 **갈리지 않으면** 무언가 고장 난 것입니다. 입장 유무와 무관하게
일관성이 비슷하게 나온다면 축이 채점에 반영되지 않고 있습니다 —
`verdicts.judge_prompt` 에 `일관성` 채점 기준이 들어 있는지부터 보십시오.

## 레이어

```
Provider  →  Agent  →  DebateEngine  →  Judge  →  Storage  →  API
```

의존은 한 방향입니다: `models ← config ← cost ← provider ← agent ← engine ← cli`

핵심 규칙 세 가지:

- **인터페이스는 `ChatProvider` 하나.** 모델을 추가한다 = 설정에 한 줄 추가한다.
  토론 로직은 안 바뀝니다.
- **재시도와 계측은 데코레이터**(`RetryingProvider`, `MeteredProvider`)입니다.
  프로바이더 구현체마다 다시 짜지 않습니다.
- **라운드 내부는 병렬, 라운드 간은 순차.** 같은 라운드 참가자는 서로 못 봅니다 —
  프롬프트 훈계가 아니라 `ContextPack` 에 진행 중 라운드를 담을 필드가 아예 없어서
  구조적으로 불가능합니다.

## fake 모드로 돌려보기 (키 불필요)

```bash
python -m debate.cli models --provider fake

python -m debate.cli run --provider-override fake --topic "원격근무는 팀 생산성을 높이는가" --agent fake-a --agent fake-b --rounds 1 --fake-latency 1800,2100
```

`FakeProvider` 는 테스트 픽스처가 아니라 1급 실행 모드입니다. 병렬성 · 재시도 ·
dropout · 컨텍스트 구성은 실제 모델보다 여기서 **더 정확하게** 검증됩니다 —
재현이 되니까요.

### 병렬성 읽는 법

```
wall 2,101ms | sum(ok=2) 3,903ms | max 2,101ms | failed=0 | waves 1
```

- `sum(ok=N)` 은 **성공한 발언만** 합산합니다. 실패한 발언은 latency 가 0 이라
  합계에 섞으면 `wall > sum` 이 되어 병렬로 잘 돈 라운드가 직렬처럼 보입니다.
- `failed=0` 인 라운드에서만 다음이 성립합니다:
  `max ≤ wall < sum(ok)` → 병렬. `wall ≈ sum(ok)` → 직렬.
- `waves` = `ceil(참가자수 / 동시성)`. 동시성 3 에 참가자 5명이면 `waves 2` 가 되고
  `wall ≈ 2 × max` 입니다. **`wall ≈ max` 는 웨이브가 1일 때만 성립하는 기준입니다.**

`failed` 가 0 이 아니면 `wall` 을 병렬성 지표로 쓰지 마세요. 죽은 참가자가 재시도
백오프로 태운 시간(3회면 대략 3초)이 벽시계를 지배해서, 나머지가 아무리 잘 병렬로
돌아도 `wall > sum(ok)` 로 나옵니다:

```
wall 3,501ms | sum(ok=2) 3,302ms | max 1,801ms | failed=1 | waves 1
```

이 줄은 "직렬이었다"가 아니라 "한 명이 재시도에 3.5초를 태웠다"로 읽습니다.

## 실제 프로바이더 붙이기

```bash
cp .env.example .env      # PowerShell: copy .env.example .env
                          # 슬롯 3개(openai / groq / openrouter)에 키를 채우세요
```

게이트웨이 하나를 경유하지 않고 **참가자마다 다른 엔드포인트를 직접 호출**합니다.
`.env` 의 슬롯에 이름을 붙이고, 참가자가 그 이름을 참조합니다:

```yaml
# config/participants.yaml
participants:
  - id: p1
    provider: openai        # → DEBATE_PROVIDER_1_*
    model: gpt-4o-mini
  - id: p2
    provider: groq          # → DEBATE_PROVIDER_2_*
    model: llama-3.3-70b-versatile
```

```bash
python -m debate.cli models --provider openai   # 모델 ID 확인
python -m debate.cli run --config config/participants.yaml --rounds 1
```

슬롯은 1..9 까지 스캔합니다. `.env.example` 이 3개를 보여줄 뿐 코드가 3개로
제한하지 않습니다. `API_KEY` 가 비면 `Authorization` 헤더를 아예 안 붙이므로
인증 없는 로컬 엔드포인트(vLLM · Ollama · LM Studio)도 그대로 붙습니다.

## 라이브 스모크 3단계

fake 모드는 **내 가정이 일관되는지**만 검증합니다. 실제 서버가 그 가정대로
응답하는지는 검증하지 못합니다. 어긋난다면 슬라이스 2~3 을 쌓기 **전에** 알아야
하므로, 키를 채우는 즉시 아래를 순서대로 돌리세요. 슬롯 하나만 있으면 됩니다.

### 준비 — 브라우저에서 하는 쪽이 쉽습니다

```
pip install -e ".[api]"
python -m uvicorn debate.api:app --host 127.0.0.1 --port 8000
```

http://localhost:8000 → **프로바이더 설정** 패널에서 프리셋(gemini / groq /
openrouter)을 고르고 키만 붙여넣으면 `.env` 가 만들어집니다. 저장 전에
**연결 테스트**로 모델 목록이 실제로 오는지 확인할 수 있습니다.

PowerShell 로 `.env` 를 손으로 만들다 BOM·따옴표·한글 인코딩으로 실패하던 단계를
없애려고 만든 화면입니다. 쓰기는 **BOM 없는 UTF-8 / LF / 권한 600 / 원자적 교체**
이고, 프로바이더 슬롯 외의 줄(다른 설정·주석)은 그대로 보존합니다.

**이 화면은 로컬에서만 열립니다.** `.env` 를 쓰고 API 키를 다루므로:

- 루프백이 아닌 주소에서 온 요청은 거부합니다 (외부 IP 에서 403, 확인함).
- `X-Forwarded-For` 같은 프록시 헤더가 붙어 있으면 거부합니다. 외부에서 그 헤더로
  로컬인 척할 수는 없지만(uvicorn 이 무시합니다, 확인함), 프록시를 거친 경로는
  외부 노출 여부를 알 수 없으므로 아예 받지 않습니다.
- `DEBATE_CONFIG_UI=off` 로 완전히 끌 수 있습니다. 여러 기기에서 붙는 구성으로
  옮긴다면 반드시 끄십시오.

> 참고: "서버가 외부에 바인드됐는가"는 요청에서 알 수 없습니다. `scope["server"]`
> 는 그 연결의 로컬 소켓 주소라, `0.0.0.0` 으로 띄우고 localhost 로 접속하면
> `127.0.0.1` 로 보입니다. 그래서 바인드가 아니라 **요청 출처**를 막습니다 —
> 실제로 지켜야 할 성질은 그쪽입니다.

### 손으로 만들려면

`.env` 에 **슬롯 1개만** 채웁니다. 나머지 두 슬롯은 비워두세요 (NAME 과 BASE_URL 이
모두 비면 그냥 무시됩니다).

```bash
cp .env.example .env          # PowerShell: copy .env.example .env
```

```dotenv
DEBATE_PROVIDER_1_NAME=openai                    # 아무 이름이나. --agent 에서 이 이름을 씁니다
DEBATE_PROVIDER_1_BASE_URL=https://api.openai.com/v1
DEBATE_PROVIDER_1_API_KEY=sk-...                 # 실제 키
```

`BASE_URL` 은 **`/v1` 까지만** 씁니다. 끝 슬래시는 있어도 없어도 같습니다
(`/v1` 과 `/v1/` 모두 정상). `/chat/completions` 는 코드가 붙이므로 쓰지 마세요.

**`.env` 는 명령을 실행하는 디렉터리에서 찾습니다.** 프로젝트 루트에서 돌리세요.
못 찾으면 에러가 어느 절대 경로를 봤는지 알려줍니다.

BOM 은 신경 쓰지 않아도 됩니다. PowerShell 의 `Out-File -Encoding utf8` 은 기본으로
BOM 을 붙이는데, `.env` 를 utf-8-sig 로 읽으므로 있든 없든 동작합니다.

### 1단계 — 연결과 인증

```bash
python -m debate.cli models --provider openai
```

**통과 조건**: 모델 ID 가 한 줄에 하나씩 출력되고 종료 코드 0.

```
gpt-4o-mini
gpt-4o
...
```

여기서 나온 ID 를 그대로 2단계에 씁니다. **눈으로 본 ID 만 쓰세요** — 기억이나
문서에서 가져온 이름은 대개 틀립니다. 이 단계는 BASE_URL · 키 · 네트워크를 한 번에
확인합니다.

### 2단계 — 실제 토론 1라운드

1단계에서 확인한 ID 로 2명을 세웁니다. 같은 프로바이더를 두 번 써도 됩니다.

```
python -m debate.cli run --topic "원격근무는 팀 생산성을 높이는가" --agent openai/gpt-4o-mini --agent openai/gpt-4o --rounds 1
```

한 줄이 길어서 쪼개고 싶다면 이어쓰기 문자가 셸마다 다릅니다 — bash 는 `\`,
PowerShell 은 백틱입니다. 헷갈리면 그냥 한 줄로 쓰세요.

**통과 조건** — 네 가지가 모두 맞아야 합니다:

1. 참가자 A · B 의 **한국어** 발언이 출력됨
2. `failed=0`
3. `sum(ok=2) > wall` (병렬로 돌았다는 뜻)
4. 종료 코드 0

```
[R1] 참가자 A  (1,842ms, openai/gpt-4o-mini)
  원격근무의 생산성 효과를 측정하려면 먼저 ...

wall 2,118ms | sum(ok=2) 3,946ms | max 2,104ms | failed=0 | waves 1
[cost] calls=2  in=1,240  out=812  $0.0000  (가격 미상: ... — 0 으로 계상)
```

발언 안에 모델명·벤더명이 새어 나오는지도 같이 봐주세요. 있으면 그대로 알려주시면
슬라이스 2 의 스크럽 규칙에 반영합니다.

### 3단계 — 토큰 집계가 진짜인지

2단계 출력의 `[cost]` 줄만 다시 봅니다.

**통과 조건**: `in=` 과 `out=` 이 **둘 다 0 이 아님**.

일부 엔드포인트는 응답에 `usage` 를 담지 않습니다. 그러면 호출은 성공하고 종료 코드도
0 인데 토큰만 0 으로 집계됩니다 — **비용 추적이 조용히 죽는 유일한 경로**라서 따로
확인합니다. 0 이면 CLI 가 이렇게 경고합니다:

```
힌트: 호출은 성공했는데 토큰이 0 입니다. ...
```

이게 뜨면 슬라이스 3 의 견적·원장 설계를 바꿔야 하니 **반드시 알려주세요.**

`가격 미상` 경고는 정상입니다 — `config/pricing.yaml` 이 아직 비어 있어서 그렇습니다.
3단계에서 확인한 실제 모델 ID 로 채우면 사라집니다.

### 발언이 잘리거나 이상할 때 — 원본 응답 받기

응답 파싱이 의심되면 원본 JSON 을 파일로 남겨서 보세요. 잘림이 모델 쪽인지
파싱 쪽인지는 원본을 봐야만 갈립니다.

```
python -m debate.cli run --topic "..." --agent gemini/<ID> --agent gemini/<ID> --rounds 1 --dump-raw ./raw
```

`./raw/01-*.json` 에 보낸 메시지와 받은 JSON 본문이 그대로 들어갑니다.
**요청 헤더는 저장하지 않습니다** — `Authorization` 이 파일에 남지 않게 하려는
것이라, 덤프를 그대로 공유해도 키는 새지 않습니다.

각 발언 아래에 `└ N자 / finish_reason=...` 이 항상 찍힙니다. 읽는 법:

| finish_reason | 뜻 |
|---|---|
| `'stop'` | 모델이 스스로 끝냈습니다. 짧다면 그건 모델의 선택입니다 |
| `'length'` | **예산에서 잘렸습니다.** `DEBATE_MAX_OUTPUT_TOKENS` 를 올리세요 |
| `None` | 엔드포인트가 이 필드를 안 줍니다. 잘림 여부를 알 수 없습니다 |

본문이 비어 있으면 성공으로 통과시키지 않고 실패로 처리합니다. 빈 발언을
그냥 두면 Judge 가 그걸 "논거 없음"으로 채점해서 결과가 조용히 망가집니다.

### 실패했을 때

`FatalError` 는 **재시도로 해결되지 않는 설정 문제**입니다. 참가자 단위로 격리되기
때문에 헤드라인이 `aborted_insufficient_participants` (종료 코드 1) 로 나오지만,
진짜 원인은 각 참가자 줄의 `── 실패:` 뒤에 있습니다. CLI 도 힌트를 같이 띄웁니다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `FatalError: 401` | `API_KEY` 가 틀렸거나 비었음 | 키 재발급/재확인. 앞뒤 공백·따옴표 주의 |
| `FatalError: 403` | 키는 맞지만 해당 모델 권한 없음 | 콘솔에서 모델 접근 권한 확인 |
| `FatalError: 404` + `model ... does not exist` | 모델 ID 오타 | 1단계 출력에서 그대로 복사 |
| `FatalError: 404` + 그 외 | `BASE_URL` 에 `/v1` 누락 | `https://host/v1` 형태로 수정 |
| 요청이 `/v1/chat/completions/chat/completions` 로 감 | `BASE_URL` 에 `/chat/completions` 를 포함시킴 | `/v1` 까지만 남기기 |
| `프로바이더를 찾을 수 없습니다` + `사용 가능: <없음>` + `이 경로에 파일이 없습니다` | 프로젝트 루트가 아닌 곳에서 실행 | 에러가 찍은 경로에 `.env` 를 두거나 루트에서 실행 |
| `프로바이더를 찾을 수 없습니다` + `사용 가능: gemini` | `--agent` 의 이름 ≠ `DEBATE_PROVIDER_*_NAME` | 두 값을 일치시키기 (에러가 인식된 이름을 보여줍니다) |
| `RetryableError: 3회 시도 모두 실패` + `429` | 레이트리밋 | `--max-concurrency 1` 로 재시도 |
| `in=0 out=0` 인데 성공 | 엔드포인트가 `usage` 미제공 | 보고 필요 (위 3단계 참조) |

`ConfigError`(종료 코드 2) 는 **LLM 을 한 번도 부르기 전에** 납니다. 과금되지 않습니다.

  2026-09 Gemini 라이브 실측으로 보정했습니다(172~319 토큰 / 250~450자 → 0.71).
  다른 벤더를 붙이면 토크나이저가 달라지므로 다시 재야 합니다.

## 참가자에게 입장을 주십시오 — 안 주면 수렴합니다

웹 UI 에서는 드롭다운으로 고릅니다 — 프로바이더를 고르면 그 슬롯의 `/models` 를
불러와 모델 목록을 채우고, 입장은 찬성/반대/중립/직접입력, 페르소나는 자유 입력입니다.
목록을 못 불러오면 그 자리에서 직접 입력으로 떨어집니다.

**Judge 를 고르는 시점에 계열이 표시됩니다.** 참가자와 같은 모델이면 "실행이
거부됩니다", 같은 계열이면 "자기편애가 점수에 남을 수 있습니다", 다르면 계열
이름을 보여줍니다. 실행이 끝난 뒤에 알면 이미 그 점수로 채점이 끝난 뒤입니다.

CLI 와 "직접 입력" 모드는 한 줄에 한 명, `provider/model | 입장 | 페르소나`.
뒤 두 칸은 선택입니다.

```
gemini/gemini-3.5-flash-lite | 찬성 | 데이터와 측정 방법을 중시하는 실증주의자
gemini/gemini-3.5-flash-lite | 반대 | 조직 문화와 암묵지 전수를 중시하는 현장주의자
openrouter/meta-llama/llama-3.3-70b:free | 중립 | 비용을 따지는 회의주의자
```

CLI 도 같은 형식입니다:

```
python -m debate.cli run --topic "..."   --agent 'gemini/x | 찬성 | 실증주의자' --agent 'gemini/y | 반대 | 현장주의자'
```

구분자가 `:` 가 아니라 **`|`** 인 이유는 모델 ID 에 콜론이 들어가기 때문입니다 —
OpenRouter 무료 모델이 `...:free` 로 끝납니다.

입장은 **각자의 헤더에만** 들어갑니다. 남의 입장이 보이면 그걸 겨냥해 말하게 되고
라운드 내 블라인드가 무의미해집니다.

### 왜 입장이 필요한가

같은 모델 2명을 입장 없이 돌리면 **둘 다 같은 편이 됩니다.** 라이브에서 R2 에
반박 대신 상대의 인용과 사례를 그대로 가져다 자기 주장을 강화했습니다.

모델 탓이 아니라 프롬프트 탓이었습니다. 예전 R2 지시는 "제2라운드 발언을
작성하십시오"가 전부였습니다. 반박을 요구하는 문장이 어디에도 없었으니, 직전
라운드 전문은 반박 대상이 아니라 **재료**로 읽힙니다. 같은 모델·같은 페르소나·
입장 없음이면 이어쓰기가 가장 자연스러운 완성입니다.

지금은 라운드마다 목적이 명시됩니다:

- **R1** — 입장을 밝히고, 반대편의 가장 유력한 반론을 스스로 짚고 답하기
- **R2+** — 생각이 다른 주장 하나를 지목해 반박. 상대 근거를 그대로 재사용 금지.
  정말 동의하면 동의한다고 **명시**하고 남는 쟁점을 드러내기

동의 자체를 막지는 않습니다. 막으면 억지 반대를 만들 뿐입니다.

### 입장 없이 돌리면 — 실측 두 가지

입장을 지정하지 않으면 둘 다 일어납니다:

1. **수렴** — R1 에서 같은 편이 되고 근거까지 거의 같아집니다.
2. **입장 교대** — R2 에서 반박은 하는데, 자기 R1 주장을 스스로 반박하며
   반대편으로 넘어갑니다. 토론이 아니라 독백 교대입니다.

반박 지시만으로 2번은 안 잡힙니다. 그래서 R2+ 에 입장 유지를 넣었습니다:

> 제1라운드에서 취한 입장을 유지하십시오. 생각이 바뀌었다면 **무엇이 당신을
> 설득했는지 명시하고** 바꾸십시오. 말없이 반대편으로 넘어가면 토론이 아니라
> 독백 교대가 됩니다.

입장 변경을 금지하지 않고 **숨기지 못하게** 합니다 — 동의를 다루는 방식과 같습니다.

**입장 자동 배정은 넣지 않았습니다.** 모델이 지지하지 않는 입장을 강제하면
역할극이 되고, 결과를 판단 근거로 쓸 수 없게 됩니다.

**반박이 없으면 Judge 도 망가집니다.** 루브릭에 `반박` 항목이 있고 `dissent` 를
반드시 채우게 되어 있어서, 실제 반박이 하나도 없으면 심판이 아무도 제기하지 않은
반론을 지어냅니다. 라이브에서 그렇게 나왔습니다.

## 판정과 비용

```
python -m debate.cli estimate --config config/participants.yaml --judge gemini/<ID>
python -m debate.cli run --config config/participants.yaml --judge gemini/<ID>
```

`estimate` 는 **LLM 을 한 번도 부르지 않습니다** (`llm_calls_made = 0`). 비용을
보고 시작 여부를 정하라고 생성과 실행이 나뉘어 있습니다. 견적은 **범위**로
나옵니다 — 출력 길이를 모르는데 단일 숫자를 내면 그건 거짓말입니다.

Judge 는 **참가자와 같은 모델이면 실행 전에 거부합니다**(`ConfigError`, 과금 0).
모델이 부족하면 `--allow-judge-overlap` 으로 명시적으로 허용할 수 있습니다.

루브릭은 5축입니다: **근거 · 논리 · 반박 · 명료성 · 일관성**.

`일관성` 은 나중에 추가했습니다. 4축만으로는 라운드마다 입장을 갈아타는 참가자를
못 잡습니다 — 실측에서 자기 R1 주장을 R2 에서 반박한 참가자들이 반박 9/8점을
받았습니다. 형식적으로는 반박 구조를 갖췄으니 그 점수가 맞고, 그래서 축이 더
필요했습니다. 설득당해 입장을 바꾼 것은 감점하지 않습니다.

편향 대응 두 가지가 들어가 있습니다:

- **자기편애** — Judge 모델을 참가자 풀에서 배제. 발언은 익명 라벨로만 전달.
- **위치 편향** — LLM 심판은 먼저/나중에 제시된 쪽을 우대하므로, 라운드마다
  제시 순서를 섞습니다.

Judge 는 참가자 수와 무관하게 **단일 패스**입니다. 대신 `prompt_tokens` 와
`finish_reason` 을 기록해서 실제로 잘리는 시점을 관측만 합니다 — 5명에서 잘리는
게 확인되면 그때 map-reduce 로 가릅니다.

## 저장된 기록 보기

`data/debates.db` (sqlite). `sqlite3` CLI 가 없으면 파이썬으로 보면 됩니다:

```python
import sqlite3
c = sqlite3.connect("data/debates.db"); c.row_factory = sqlite3.Row

# 익명화 검증 — Judge 에게 실제로 보낸 프롬프트를 그대로 검사
prompt = c.execute("select judge_prompt from verdicts").fetchone()[0]
models = [r[0] for r in c.execute("select distinct model from participants")]
print([m for m in models if m in prompt])      # [] 여야 정상

# 라벨 -> 모델 매핑 (DB 에만 있고 프롬프트에는 없음)
print(dict(c.execute("select anon_label, model from participants")))

# 용도별 · 라운드별 비용
for r in c.execute("select purpose, count(*), sum(in_tok), sum(out_tok)"
                   " from llm_calls group by purpose"):
    print(tuple(r))
```

재개(resume)는 지원하지 않습니다. 사후 기록만 필요하다는 결정에 따라 체크포인트
없이 완료 시점에 한 번 씁니다.

### 느린 참가자를 기다리는 동안 화면에 보이는 것

참가자 카드는 네 상태를 구분합니다. `RoundStarted` 의 활성 목록과 별개로
`utterance_started` 가 **세마포어를 얻은 뒤에** 나가므로, 동시성 3에 참가자 5명이면
3명은 "말하는 중", 2명은 "차례 대기"로 갈립니다.

```
참가자 A  [말하는 중]  0.5초 경과      ← 0.1초마다 갱신되는 타이머
참가자 B  [완료]      0.2초 · 122tok
참가자 C  [말하는 중]  0.5초 경과
```

상단 지표는 **항상** 보입니다(sticky). 무료 티어에서는 금액이 0이라
**요청 수와 총 토큰을 주 지표로 크게** 놓고, 금액은 `$0 (무료)` 로 작게 씁니다.

## 사람의 개입

라운드 사이에 지시를 넣습니다. 게이트가 열리면 카운트다운과 함께 입력창이 뜨고,
`지시 보내고 진행` 또는 `지시 없이 바로 진행` 으로 즉시 재개할 수 있습니다.

- **1회용** — 지정된 라운드에만 들어가고, 이후에는 요약본에 흔적 한 줄로만 남습니다.
- **전체 브로드캐스트** — 모든 참가자가 같은 지시를 봅니다.
- **스크럽을 통과합니다** — 지시문에 모델명을 쓰면 그게 Judge 프롬프트까지 흘러갑니다.
- **타임아웃은 실패가 아니라 진행** — 아무도 안 들어오면 지시 없이 다음 라운드로.

`gate_timeout_s: 0` 이면 대기 자체를 하지 않습니다(기본값).

### 브라우저를 닫으면 — 실측 결과

**토론은 날아가지 않습니다.** 실행은 서버의 백그라운드 태스크라 SSE 연결과 수명이
분리돼 있습니다. 게이트가 열린 순간(가장 위험한 시점)에 연결을 끊고 측정한 결과:

```
 4.0초: 게이트 열림 → 연결 끊음
23.2초: 서버 상태 = completed (닫은 뒤 19.1초 더 진행)
        sqlite: status=completed rounds=3 발언=6 판정=1
        재접속 시 26개 이벤트 재생 (끊기 전 본 것 9개)
```

`?id=<debate_id>` 로 다시 열면 버퍼된 이벤트가 재생돼 화면이 복구됩니다.

### 재연결이 화면을 망가뜨리지 않는 이유

EventSource 는 **정상 종료를 포함해 연결이 닫히면 자동으로 다시 붙습니다.** 그래서
스트림을 그냥 닫아두면 3초마다 재접속이 일어나고, 서버가 버퍼를 처음부터 재생해
화면이 무한히 중복 누적됩니다. 실측에서 20회 재연결에 발언이 9개 → 36개로 불어났습니다.

두 겹으로 막습니다:

- **서버** — 이벤트마다 `id: <seq>` 를 붙입니다. 브라우저는 재연결 시 그 값을
  `Last-Event-ID` 헤더로 돌려주고, 서버는 **그 이후만** 보냅니다. 헤더가 없으면
  (새 탭·새로고침) 전체를 재생합니다 — DOM 이 비어 있으니 전부 필요합니다.
  EventSource 가 자동 재연결일 때만 헤더를 붙이므로 이 구분은 공짜로 얻어집니다.
- **클라이언트** — 마지막으로 그린 `seq` 를 기억하고 그 이하는 무시합니다.
  서버가 실수로 다시 보내도 화면은 멱등합니다. 그리고 `finished` 를 받으면
  `es.close()` 로 재연결 자체를 끊습니다.

게이트 대기(최대 120초) 중에는 15초마다 keepalive 주석을 보내 연결을 유지합니다 —
45초 무응답 구간에서 재연결 0회를 확인했습니다.

### 어떤 단계가 실패해도 스트림은 닫힙니다

`finished` 가 안 나가면 EventSource 는 끊긴 줄 알고 영원히 재연결합니다. 그래서
종료 절차(`DebateSession.finalize`)는 각 단계를 따로 감싸고, 저장이 터지든
판정이 터지든 **finished 는 반드시 방출합니다.**

| 실패 | 화면에 보이는 것 |
|---|---|
| 심판 무응답·오류 | `판정을 받지 못했습니다` + 사유, 상태줄에 `· 판정 실패` |
| 기록 저장 실패 | 상태줄에 `· 저장 실패`, 로그에 사유 |
| 참가자 전원 실패 | `종료 — 중단 — 생존 참가자 부족` |

`finished` 는 **토론의 실제 결과**를 싣습니다. 세션 상태(`run_status`)는 "run() 이
예외 없이 끝났다"는 뜻일 뿐이라, 그것만 쓰면 전원 죽어 중단된 토론도 `완료` 로
보입니다.

심판에는 별도 시한(`DEBATE_JUDGE_TIMEOUT_S`, 기본 300초)이 걸립니다. 재시도
예산은 기본값에서 6분인데, 그동안 아무 이벤트도 안 나가면 화면은 멈춘 것과
구분되지 않습니다. 기다리는 동안 화면에는 **판정 중 + 경과 시간**이 돕니다.

### 판정이 잘리는 문제

라이브에서 심판 출력이 JSON 중간에서 끊겼습니다. 형식 문제가 아니라 **출력 토큰
부족**이었습니다. 내용만 따지면 쟁점 4개·참가자 2명에 1,000 토큰 남짓인데 4,096 을
주고도 모자랐는데, 사고 과정을 출력 예산에서 함께 쓰는 모델로 보입니다 — 같은
실행에서 참가자는 2초, 심판은 3~4분 걸렸습니다.

- 예산은 `judge.required_output_tokens()` 가 계산합니다: **사고 몫(고정 6,000) +
  내용 몫(쟁점·참가자 수에 비례) × 1.5**. 사고 몫을 배수로 처리하면 쟁점이 적을
  때 모자라고 많을 때 과합니다. `DEBATE_JUDGE_MAX_TOKENS` 로 덮어쓸 수 있습니다.
- 프롬프트가 reasoning 을 **쟁점당 2~3문장(120자)** 으로 묶고, conclusion·dissent
  도 같게 제한합니다.
- 길이 때문에 잘렸으면 복구 시도가 **예산을 2배로 늘리면서 동시에 더 짧게 쓰라고**
  지시합니다. 예산만 올리면 장황한 모델은 늘어난 만큼 더 쓰고, 지시만 하면 이미
  모자란 예산이 그대로입니다. 잘린 본문은 되돌려 보내지 않습니다 — 예산만 먹습니다.
- **잘림과 형식 오류를 구분해서 표시합니다.** 둘을 "파싱 실패"로 묶으면 예산
  문제를 프롬프트 문제로 오해합니다.

**진짜 위험은 서버 프로세스가 죽는 경우입니다.** 체크포인트가 없어서 진행분이
전부 사라집니다. 노출 창은 관측된 지연(54.3초) 기준으로:

| 게이트 | 최악 진행시간 | 비고 |
|---|---|---|
| 0초 (기본) | 2.7분 | 개입 없음 |
| 60초 | 4.7분 | |
| **120초 (권장)** | **6.7분** | 라운드를 읽고 한 줄 치기에 충분 |
| 300초 | 12.7분 | 잊고 닫은 탭이 오래 붙잡음 |

**체크포인트는 넣지 않았습니다.** 6.7분 노출은 로컬에서 직접 띄우는 도구로는
감수할 만하고, 재개를 넣으면 엔진이 상태 기반으로 재작성됩니다. 서버를 오래
띄워두거나 여러 사람이 쓰기 시작하면 그때 다시 판단할 문제입니다.

토론 중간에 사람이 지시를 넣는 기능은 아직 **동작하지 않습니다.** 다만 나중에
끼울 자리는 이미 있고, 지금은 항상 비어 있습니다:

| 자리 | 위치 | 현재 |
|---|---|---|
| `ContextPack.directives` | 쟁점 뒤, 차례 지시 앞에 렌더 | 항상 빈 튜플 |
| `InterventionGate` | 매 라운드 시작 전 엔진이 호출 | `NoIntervention` (즉시 빈 튜플) |
| 지시문 스크럽 | `ContextBuilder._scrub_directives` | 참가자 발언과 동일 경로 |
| 지시 흔적 | `DebateState.directive_trace` → 요약 프롬프트 | 비어 있으면 규칙 자체가 빠짐 |

확정된 규칙:

- **1회용.** 지정된 라운드에만 들어가고, 이후에는 요약본에 "사회자가 X를
  지시함" 한 줄로만 남습니다. 누적하면 라운드가 갈수록 지시문이 헤더처럼 쌓입니다.
- **전체 브로드캐스트만.** 참가자별 개별 지시는 컨텍스트를 참가자마다 갈라놓아
  Judge 가 "왜 이 참가자만 이 얘길 하지"를 판단할 근거를 잃습니다.
- **지시문도 스크럽을 통과합니다.** 사용자는 어느 참가자가 어느 모델인지 알기
  때문에, 지시문이 모델명 누설의 가장 쉬운 경로입니다.

### 알려진 한계 — Judge 격리는 계열 내 자기편애를 막지 못합니다

`allow_judge_model_overlap=False` 검사는 **모델 ID 만 비교**합니다. 그래서

    참가자: gemini-2.x-flash   +   Judge: gemini-2.x-pro

같은 조합은 **검사를 통과합니다.** 그런데 이 규칙이 애초에 막으려던 것은
자기편애이고, 그건 같은 벤더·같은 계열 모델 사이에서도 상당 부분 남습니다.
즉 **검사는 통과하는데 목적은 달성 못 하는 상태**입니다.

프로바이더 키가 하나뿐이면 참가자도 Judge 도 전부 한 계열이 되므로 실제로 자주
걸립니다. 슬라이스 3 에서 두 갈래 중 하나를 골라야 합니다:

1. 계열(vendor/family) 단위 경고를 추가 — 계열 판정을 무엇으로 할지가 문제
   (모델 ID 접두사? 프로바이더 이름? 수동 매핑표?). 오탐이 나면 정상 설정이
   막힙니다.
2. 문서에 한계로만 명시하고 검사는 ID 단위로 유지 — 구현은 안 늘지만 사용자가
   구멍을 모르고 지나갈 수 있습니다.

**막지 않기로 했습니다.** 이유 둘:

1. 프로바이더 키가 하나뿐이면 계열 경고가 **매 실행마다** 뜹니다. 기본 설정에서
   뜨는 경고는 노이즈이고, 노이즈가 되면 진짜 경고도 같이 무시됩니다.
2. 계열 판정 기준 자체가 애매합니다. 접두사로 자를지 벤더로 자를지, OpenRouter
   경유는 어떻게 볼지. 오탐이 나면 정상 설정이 막힙니다.

**대신 관측 가능하게 두었습니다.** 실행 끝에 사실 한 줄이 찍히고(경고 아님),
`debates` 테이블에 `judge_family` · `participant_families` ·
`judge_shares_family` 가 기록됩니다:

```
judge: gpt 계열 (참가자와 다름; 참가자 계열: gemini)
```

### 벤더를 바꾸면 점수가 얼마나 달라지는가 — 실측

두 번째 프로바이더(Groq)를 붙여 **같은 토론 구조**에 심판만 바꿔 봤습니다.
참가자는 Gemini 2명(찬성/반대 지정), 심판만 Gemini → Groq 로 교체했습니다.

| | Gemini 심판 | Groq 심판 (`openai/gpt-oss-120b`) |
|---|---|---|
| 루브릭 합계 | 44 / 40 | **39 / 33** |
| 최고점 | 10점 다수 | **9점 하나** |
| 참가자 간 격차 | 4점 | **6점** |
| 일관성 (둘 다 유지) | 10 / 10 | **8 / 8** |

**같은 토론인데 채점자 벤더가 바뀌면 이만큼 달라집니다.** 절대 점수는 심판
모델의 성향에 크게 좌우되므로, 서로 다른 실행의 점수를 비교하려면 **심판을
고정해야 합니다.**

이게 자기편애 차단이 필요한 이유의 실증이기도 합니다. 채점자가 바뀌는 것만으로
합계가 11%~18% 움직이는데, 그 채점자가 참가자 중 하나와 같은 모델이라면 그
편향이 어느 방향인지 알 수 없습니다.

계열이 다른 심판을 쓰면 이 항목은 해소됩니다. Groq 무료 키로 충분합니다.
